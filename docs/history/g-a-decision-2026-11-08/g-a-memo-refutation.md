## Verdict

The recommendation stands; several of its supporting sentences do not. Nothing refuted here touches the lean's load-bearing evidence: the three-to-one import map, the toolkit-only authored content the canonical shape cannot hold (298 paths in 14 workbooks once the lossless `General` rows are removed), the canonical-only fields that are derivable for imported documents, the empty-formula cells and spilled-cell caches the toolkit holds and the canonical reader refuses, and the four spec 14 sub-answers. But four claims the memo presents as evidence are wrong as stated: the "three reversal conditions" are spec 09's three *reasons* relabelled and the "two assets re-created" are not on spec 09's asset list (R2, C1); the inventory sentence inverts how intake computes the inventory (R3); step 0's edges do not sniff shapes (R4); and "nothing a toolkit document loses" is contradicted by the memo's own scenario round trip (R1). The binding amendment carries two costs the memo does not state (W7, W8), and the "one more version" cost is understated with an alternative untested (W9). ### 2(a). The `required` rule: default true for v2-written bindings, `required: false` on every migrated v1 binding

**Does anything assume `required` is true?** No. Every reader of the flag branches on it rather than assuming it:

- Value validators: `python_engine.py:184-186` and `toolkit.rs:1036-1042` return early on a blank when `required` is false, so `set_inputs`/`preview_inputs` (`_input_edits`, `python_engine.py:307-321`; `validate_inputs`, `toolkit.rs:1079-1105`) accept a blank bound cell for a migrated binding and still type-check a non-blank one against `kind`.
- Agent `describe` passes the normalised binding through unchanged (`agent.py:318`; `agent.rs:157`); the TS client types `inputs` as `Json` (`client.ts:26`); `web/forge-engine` has no reader of the flag.
- Spec 12 reads the binding `{kind, required, min, max, choices}` as the record it preserves (`12-*.md:149, 284`) and assumes nothing about the value.

**A consumer class the memo does not list.** Both toolkit xlsx writers serialize `required` into the exported package: the data-validation formula is wrapped in `OR(ISBLANK(addr), …)` when `required` is false and the element carries `allowBlank="1"` (`xlsx.py:733-734, 894`; `xlsx.rs:2104-2106, 2472`), and on re-export of an imported package the existing validation's `allowBlank` and formula are verified against the binding (`xlsx.py:943-952`; `xlsx.rs:2556-2568`). Consequence of the rule: a migrated v1 binding exported through a v2 toolkit writer carries a validation that allows blank; a v2-authored binding carries one that does not. Nothing is lost (canonical v1 export writes no data validations at all: no `dataValidation` in `canonical_xlsx.py`), but it is a difference visible in exported files and in Excel that the memo should state beside the `set_inputs` behaviour.

**Should the migrator instead write "required: true unless the bound cell is blank at migration"?** No, on four grounds:

1. It makes migration state-dependent: two v1 documents with identical bindings migrate to different v2 bindings according to what the cells held at that moment. Spec 06's migrator is a shape function ("a v1 binding becomes `{cell, type: null, required: false, constraints: {}}`") and its test `v1_fixture_migrates_to_v2` expects one output per input document.
2. It is the inference from the current cell value that the memo rejects for `kind` (spec 06: intake "never guesses"); the two fields should follow one rule.
3. It gains refusals: a filled v1 binding becomes required, so blanking it later through `set_inputs` is refused (`required input is blank`), which no canonical v1 document ever refused. The memo's sentence "no v1 document gains a refusal it did not have" holds only under the constant `required: false`.
4. The exported `allowBlank` would then also depend on cell state at migration (point above).

The memo's rule survives. One cost it should state: a migrated document whose author wants the primitives-layer rule must set `required: true` explicitly in v2, one edit per binding, in the document, not an inference.

**One open item on the step 0 / step 2 difference.** The memo says "step 2's migrator differs from step 0 on this one field, deliberately". Spec 09 step 0 says the two edges "become the migrator in step 6", and `to_toolkit` stamps `required: true` through the toolkit default in both languages (`convert.py:154` builds `{sheet, address, kind}` and `_normalize_model` fills `required: True`; `convert.rs:171-180` likewise), pinned by the fixture (`canonical_cases/authored-two-sheets` expects `required: True` on the converted binding). If `to_toolkit` is what step 6 uses to read old v1 canonical documents, either it gains the migrated-binding rule (and that fixture case changes) or step 6's migrator is a different function. The memo should say which. No interim inconsistency today: at the boundary in steps 3-4, v1 canonical bindings without caller-supplied kinds are dropped, not stamped.
