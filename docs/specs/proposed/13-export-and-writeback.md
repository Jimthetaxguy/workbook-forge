# 13 — Export and writeback

## Problem

A session's state leaves the process today by four paths that grew separately and refuse different things. Both patch writers refuse to overwrite the source (`python/workbook_forge/xlsx.py:1101-1102`; `rust/src/xlsx.rs:1955-1967`) and refuse any existing destination (`xlsx.py:1103-1104`; `xlsx.rs:465-467`); the canonical writer refuses an existing destination and has no source to protect (`python/workbook_forge/canonical_xlsx.py:112-113`); the browser returns bytes and never sees a path (`rust/src/wasm.rs:4,216-219`); both agents write one new file into a host directory (`python/workbook_forge/agent.py:341-348`; `rust/src/agent.rs:271-280`). The preservation baseline is defined as content "used to patch supported changes without rereading or rewriting the original file" (`CONTEXT.md:66`). This proposal takes as its premise that a caller may also ask for an explicit update of the original file, and later for a live Excel adapter, and that continuous synchronisation is not required. Original-file update is therefore a new operation with its own contract, not a refusal to remove: every path that refuses today keeps its refusal.

What the writers preserve today is narrower than the corpus check suggests. Both set full recalculation on open and remove the calc chain on every export, edits or none (`python/workbook_forge/workbook.py:1954-1976`; `xlsx.rs:2490-2543,2968`); that is what four of the five `MAY_CHANGE` parts are for (`tools/corpus_check.py:72-78`; the fifth, `xl/sharedStrings.xml`, is listed but no writer touches it). Both also rewrite every sheet part that holds a formula cell whose value is in the calculation report, to refresh its cache: Python collects a cache value for every such cell (`xlsx.py:1137-1148`), writes each through `Workbook` (`:1177-1179`), which pulls the part into `_changed_sheets` (`workbook.py:1251-1254`) and re-serialises it through `ET.tostring` (`:1985-1990`), which does not preserve bytes; Rust computes a cache for every formula cell and replaces the cell even when its content did not change (`xlsx.rs:2929-2939`), rewriting the part whenever any cell was replaced (`:2961-2965`). With no bound outputs both closures select every formula cell (`python/workbook_forge/python_engine.py:415`; `rust/src/toolkit.rs:1363-1365`), so an export with no edits re-serialises every formula-bearing sheet. The corpus check reports no finding only because its lane binds the edited cell as the sole output (`corpus_check.py:262`), and the byte-identity test (`python/tests/test_xlsx_features.py:66-71`) uses fixtures with no formula on a non-edited sheet; `fixtures/corpus/hb_defined_names.xlsx`, whose second sheet holds eight formulas and third holds two, is in neither.

Three things are missing for the update operation. First, a definition of when the original is still the file the session imported: spec 10 supplies the identity (`source.fingerprint`) and leaves the test to James (its open question "same baseline"); the conflict rule, staging and recovery are gate G-C (`CONTEXT.md:33`; `docs/specs/proposed/README.md`). Second, a plan a caller can read before publication: today a blocked-cell edit is discovered while patching (`xlsx.py:1002-1005`; `xlsx.rs:2940-2942`) and structural refusals come first-hit (`xlsx.py:979-989`; `xlsx.rs:2865-2873`). Third, an identity: the agent reports `{filename, revision, bytes}` and no fingerprint (`agent.py:357`; `agent.rs:297`); only the browser log and the canonical receipt report a `sha256` of what was written (`rust/src/event_log.rs:314-320`; `python/workbook_forge/canonical_roundtrip.py:143`). One defect is independent of all three: in the race path `export_xlsx` raises `FileExistsError(target)` (`xlsx.py:1104`) and the Python agent forwards `str(error)` as the `export_error` message (`agent.py:353-355`), which is the resolved machine path. That is fixed on its own, before G-C.

## Outcome

- Every destination intention has one contract: what it needs from the session and from the preservation envelope, what it produces, and the `sha256:` identity it reports.
- A caller can ask for the plan of an export, read what will be preserved byte for byte, what will be rewritten and why (an edit, or a cache refresh), what is refused and what recalculates on open, and decline before anything is written.
- The original file can be updated on explicit request, only when it is still the file the session imported, with the previous bytes retained until the caller releases them, and with a report that states which protection the destination offered and which windows stayed open.
- Downloaded bytes and the live Excel adapter sit on the same map, so neither is specified by accident later.

## Scope

- The five intentions and their table (Design 1); export planning (Design 2); the original-file update contract with its race analysis and crash behaviour (Design 3); the browser's downloaded bytes against writeback (Design 4); the live Excel adapter's destination contract and the harness rules it keeps (Design 5); refusal codes and the report shape (Design 6); evidence (Design 7).
- Library and CLI surfaces in both languages. A CLI verb for the plan and the update is proposed under `workbook-forge` beside `scenario` and `calculate --xlsx`; its name is not decided here.
- Claims about POSIX filesystems, operating systems and Excel that no file in the repository backs are marked **[assumption]** or **[unobserved]**. An implementation verifies each assumption on the destination filesystem and the report names the ones it relied on.

## Non-goals

- Continuous synchronisation, file watching, or merging a destination that changed.
- Removing the source-overwrite refusal from intentions 1 to 3.
- Implementing the live Excel adapter. Design 5 is its destination contract only; nothing in it runs Excel.
- A portable serialization of the envelope (spec 10 Design 4 leaves the container open); this spec names what writeback needs from it.
- Any `schema_version` or `model_version` change; any change to the agent protocol wire format or the browser command API (G-D).

`cache_refresh` is the largest correction this proposal makes to the picture the corpus check gives. With no bound outputs the closure is every formula cell, so the plan for an unedited export of a workbook with a formula on every sheet lists every sheet `rewritten`. A plan that wants to preserve more has two routes: bind outputs, as the corpus lane does, which shrinks the closure; or change the writers to re-serialise a cell only when its cache differs from the cached value already in the part (Rust already compares `content_changed` at `xlsx.rs:2931` and would compare the cache too; Python's `Workbook` re-serialises any part it touched and would need to skip untouched caches). The second is proposed as part of the implementation, not assumed; Design 7 bullet 2 measures it on a fixture with formulas on an unedited sheet.

A plan with any `refused` entry is complete and returned; the write operation refuses with the first code. Plans are advisory: the write re-runs every check against the revision it publishes, as both writers already re-check the revision after patching (`xlsx.py:1183-1184`; `xlsx.rs:1943-1945`). For intention 3 the plan is computed in the worker and returned with the bytes; it has no `destination` and no `protection`.

### 3. The original-file update contract

Eight steps. Each is a named phase written to a journal beside the staged file (`<name>.xlsx.forge-writeback.json`, never a machine path inside it) so a later run can finish or reverse. The journal is created exclusively, and that creation is the mutual exclusion between two writebacks on one target: the second refuses `destination_conflict` with reason `journal_present`. Every later update to the journal is written to a sibling and renamed into place, so a crash never leaves a truncated journal. A stale journal from a crashed run blocks later writebacks until `--recover` has finished or reversed it; no journal is ever deleted silently. No writer in the repository renames over an existing file today (`os.replace`, `os.rename` and `fs::rename` appear nowhere under `python/workbook_forge` or `rust/src`), so the apply step has no in-repo precedent and its assumptions are listed where they are used.

1. **Identify target and source.** Target = `source.handle` resolved as the importer resolved it (`Path.resolve()`, `workbook.py:694`; `fs::canonicalize`, `xlsx.rs:1472`), which is why symlinks need no separate treatment below. Source identity = `source.fingerprint`. A bytes import has no handle (`xlsx.rs:1486`): `writeback_unsupported`. A target that is missing or unreadable is `destination_changed` with `observed: absent`. The session revision must equal the caller's `expected_revision`: otherwise `revision_conflict`. Once the document carries `metadata.source.fingerprint` (spec 10 Design 5; writing it is G-A), an envelope whose fingerprint disagrees with it is `envelope_mismatch`; until then the envelope is session-held and this check has nothing to compare, which is why spec 10 and G-A are dependencies of this contract rather than parts of it.
2. **Compute the change plan.** Design 2 for intention 4. Any `refused` entry stops here, before the destination is read.
3. **Establish target compatibility.** Read the destination's bytes once and hash them. Two tests, both presented for G-C:
   - **Strict:** `content_fingerprint(destination bytes) == source.fingerprint`. The browser log records this identity for its baseline (`event_log.rs:46-58`) and `replay` enforces it on replay input (`:612-630`); nothing enforces it against a destination today, because no path has one. Any other change, even to a sheet the plan does not touch, is `destination_changed`; the caller re-imports and replays its edits. Strict has a property the weaker test lacks: its meaning does not depend on the model of what the writers preserve, which this proposal's first draft got wrong (Design 2).
   - **Weaker** (spec 10's alternative): decode the destination with the importer; every part the plan lists as `preserved` must equal the baseline's bytes for that part; `rewritten` and `removed` parts may differ. Because `rewritten` includes every cache-refreshed sheet, the protected set is smaller than the complement of `MAY_CHANGE`: on a workbook with a formula on every sheet, the weaker test protects only the non-sheet parts. It also has a hole whose size depends on the baseline: when the baseline carries a calcChain, `[Content_Types].xml` and the workbook `.rels` are `rewritten`, so a sheet another writer added would pass the test and be dropped by the apply; when it does not, both parts are `preserved` and the added sheet is caught. The weaker test must therefore also require the sheet-entry list and the part set to be unchanged in every case, and even then it lets the other writer's change to an untouched sheet stand while this session's `baseline.document` no longer describes the file.
   Recommendation: strict, as spec 10 recommends. If James chooses the weaker test, the part-set clause is mandatory, the `rewritten` set it relies on must include `cache_refresh`, and the report must name the parts that differed and were kept.
4. **Stage beside the target.** Build the package from the baseline exactly as `export_xlsx` and `export_package` do (`xlsx.py:1155-1180`; `xlsx.rs:1933-1942`), encode, re-open the staged bytes (`xlsx.py:1181-1182`; `xlsx.rs:491-495`), write `.<name>.forge-stage-<pid>-<n>.xlsx` in the target's directory with exclusive creation (the scheme `publish` uses, `xlsx.rs:471-479`), then sync the file and its directory. Today only Rust syncs the file (`xlsx.rs:482`); Python's `save_as` never syncs (`fsync` appears nowhere under `python/workbook_forge`); neither syncs the directory **[assumption: on POSIX the directory sync is what makes the new entry durable]**. Stage, recovery and target are taken to be on one filesystem **[assumption]**, as today's writers already assume through `dir=target.parent` (`xlsx.py:1155,1185`; `xlsx.rs:471,483`).
5. **Retain recovery before apply.** Hard-link the target to `<name>.xlsx.forge-recovery-<first 8 hex of fingerprint>-<n>`, choosing the first free `n`; the journal records the name. **[assumption: a hard link shares the target's inode, so a concurrent in-place writer changes both.]** A generation left by an earlier import of the same bytes carries the same eight hex digits and is not reused as the detector, because it need not share the current target's inode. Hash the link; it must still equal step 3's hash. Where hard links are refused, a copy is retained instead and the journal records `recovery: copy`: a copy is a recovery generation but not an in-place-writer detector, so `hard_link_and_rename` is unavailable under it and only `exchange` or `lock` may apply (step 6). If no recovery can be retained, stop with `destination_conflict` (`recovery_unavailable`): the update never runs without it.
6. **Apply with destination-appropriate protection**, strongest first:
   - **exchange:** an atomic swap of staged and target where the destination filesystem offers one **[assumption: an exchange flag on rename exists on some current Linux and macOS filesystems; it is a filesystem property, not an operating-system one, and the adapter probes it rather than assuming it]**. After the swap the previous target sits at the stage path; hash it: equal to step 3 means commit; unequal means swap back and report `destination_changed`. The swap-back is a second exchange with its own window: a replace-writer landing between the two swaps has its new inode moved to the stage path, where the operation must keep it as a foreign generation for `--recover` to list, never clean. Exchange therefore converts an undetected loss into a detected one and moves the residual window to the reversal path, where it is reportable; it does not remove it.
   - **lock:** an exclusive lock that the destination's other writers honour, held from step 3 through step 7, then `rename(staged, target)`. The lock cannot sit on the target's inode: after the rename it would sit on the old inode, now the recovery generation, and the new target would be unlocked **[assumption: advisory locks are per inode]**. It sits on the journal file, which is already the token between two writebacks, so it protects only against writers that honour that sidecar; a spreadsheet application's own lock file is not that lock.
   - **hard-link-and-rename:** step 5's link (never a copy), `rename(staged, target)` **[assumption: rename atomically replaces an existing entry on one filesystem]**, then re-hash the recovery link. An in-place writer that finished before the rename is detected (the shared inode changed): `rename(recovery, target)` restores their bytes and the report says `destination_changed`. An in-place writer still holding the file open after the rename keeps writing to the old inode, which is now the recovery generation; the re-hash cannot separate that from a finished write and the restoring rename races the continuing writes; the journal records `window: open_writer_unclosed`. A replace-writer is **not** detected: one that wrote a new inode and renamed it over the target between step 3 and the rename has been overwritten, and the recovery link still hashes equal; the journal records `window: replace_writer_unclosed`. These are the races a check-then-write does not close; closing them is what the destination adapter must provide, as `exchange` or `lock`.
   - **refuse:** without `exchange` or `lock` the operation refuses with `destination_conflict` (`no_protection`), unless James decides on an explicit opt-in (`accept_unclosed_window: true`) under which hard-link-and-rename runs and the report states every window (open question 3). Under `recovery: copy` the opt-in is refused outright, because nothing would detect anything. Where the filesystem offers no atomic rename over an existing file, the adapter says so and the operation refuses with `writeback_unsupported` (`no_atomic_rename`); it never copies over the target.
   The existing create-new paths need none of this: `os.link` and `fs::hard_link` fail when the target exists (`xlsx.py:1185`; `xlsx.rs:483`) **[assumption: `link` fails with `EEXIST`]**, so the advisory `exists()` checks (`xlsx.py:1103`; `xlsx.rs:465`) are already backed by an atomic refusal.
7. **Report outcome and new identity.** Design 6 shape: identity before, identity after (`sha256:` of the bytes re-read from the destination), the recovery handle and its hash, the protection used and every window, the assumptions relied on, the plan. The session's envelope is replaced by one derived from the written bytes with the current document as `baseline.document` (spec 10 Design 2); the revision does not move, as agent export leaves it today (`docs/agent-protocol.md:139`).
8. **Release recovery.** `release_recovery(handle)` deletes the generation on the caller's word; or a bounded `generations: N` policy deletes the oldest when the N+1th is retained. The update itself never deletes a generation and never deletes on failure (open question 2). Releasing a hard-link generation cannot lose the original: unlinking one of two links leaves the other, and if the apply never ran the target keeps its own entry.

**If the process dies between stage and apply.** After step 4 and before step 5 a stage file and a journal remain and the target is untouched; there is no recovery yet, so the next run restarts from step 3 and re-establishes compatibility before retaining one. After step 5 the target is still untouched and a recovery generation exists. Under `exchange`, a crash in step 6 leaves either the swap done (the journal says `applying`, the stage path holds the previous bytes; the next run hashes them and either completes the report or swaps back) or not done. Under rename, a crash after the rename but before the journal's `applied` entry leaves the target updated and the recovery link valid; the next run hashes target and recovery and completes. A stage file with no journal, a journal whose recorded stage hash does not match the stage file, a journal that does not parse (`journal_unreadable`), and a foreign generation left at the stage path by an exchange reversal are listed by a `--recover` command and left in place; none is deleted silently. Today's writers leave a `.workbook-forge-*` directory, a `.tmp` file or a `.workbook_forge-*.xlsx` file after a crash (`xlsx.py:1155`; `xlsx.rs:471-487`; `workbook.py:1997-1999`) and nothing resumes or lists them.

### 4. Downloaded bytes differ from writeback

The browser has no intention 4. The host owns the file (`wasm.rs:4`), the engine returns bytes (`engine.ts:364`), and the demo hands them to a download whose name the page chooses (`main.ts:130-134`). What ties the bytes to a revision is the log: `export {includeLog:true}` appends `session.exported{revision, xlsx_sha256}` and returns `{bytes, log, logName}` (`engine.ts:365-368`; `event_log.rs:314-327`; pinned by `web/forge-engine/test/engine.node.test.mjs:205-212` and `rust/tests/event_log.rs:474-483`). The baseline is identified the same way, `session.opened.baseline{sha256, bytes}` (`event_log.rs:46-58`; set at `wasm.rs:228`), and `replay` refuses other bytes with `baseline_mismatch` (`event_log.rs:612-630`). The browser therefore already records the strict identity on both ends and enforces it on replay input, with no destination at all: a host that later wants intention 4 from a downloaded artifact must present the file and the log together, and the compatibility test is `sha256(file) == session.opened.baseline.sha256`. Without `includeLog` the bytes carry no revision and no identity (`engine.ts:364`). This spec asks the demo to default `includeLog` on and offer the log beside the download under `logName`, so every downloaded artifact is traceable to the revision that produced it; the engine and protocol do not change.

### 5. The live Excel adapter as a destination

Nothing in this design is observed. No committed receipt records a save stage or `full_rebuild_invoked: true` (`receipts/` holds the canonical scenario only), and the house rule puts every Excel claim below under **[unobserved]** until spec 01's receipt or a later one records it. Excel holds a copy of the workbook in memory, so "the destination's current bytes" are two things: the saved file and the open document. The adapter would:

- **Inspect:** whether a workbook of the expected name is open and at the expected path (`exists workbook`, `full name`, `excel_oracle.py:1139-1144`); whether any other workbook is open (`:1130`); the global calculation and iteration settings, read-only, with the preflight that refuses when they are unobservable or differ (`:1131-1134,1120-1125`); whether the open document has unsaved changes **[unobserved: no harness code reads such a property; the only `unsaved` the harness knows is the live-scenario status]**.
- **Compatibility:** the saved file passes Design 3 step 3 **and** the open document has no unsaved changes; otherwise `destination_changed`. The user's unsaved edits are a concurrent writer.
- **Apply:** ask Excel to set the cells the plan rewrites, as the harness applies declared edits (`:1145`); never patch the file under an open workbook; ask for the full rebuild (`:1146-1147`) instead of relying on `fullCalcOnLoad`; save in place with `save targetBook` **[unobserved: the claim that this is the one save form that works after a rebuild without a dialog rests on a docstring, `excel_oracle.py:247-257`, not on a receipt; `docs/excel-observations.md:169` records a `-50` in a different context]**.
- **Request:** nothing it cannot observe; a setting it needs and cannot read is a `blocked` outcome, not an assumption (`docs/excel-observations.md:81-84`).
- **Reconcile:** re-read the saved bytes, reimport them with the toolkit importer (`_model_view`, `:926`), compare values to the session's calculation by the contract's tolerances and volatile rules, record `saved_workbook_sha256` as the new identity (`:1487,1535`), and replace the envelope.

It inherits the writeback conflict model because Excel is a writer that honours none of our locks and **[unobserved]** replaces the file on save: only compatibility-before and identity-after are available, the report must say `protection: verify_after`, and reconciliation is the check. The harness rules it must keep: never change global calculation, iteration or security settings (`excel_oracle.py:1120-1125`; `docs/excel-observations.md:40-41,77-78`); never open, close or save a workbook the caller did not name, and refuse while another workbook is open because the full rebuild is application-wide (`excel_oracle.py:1130`; `docs/excel-observations.md:72-75`); no cleanup commands after an uncertain failure (`docs/excel-observations.md:43-45`); scratch copies, not the caller's file, for observations (`excel_oracle.py:1465`; `docs/excel-observations.md:50`); receipts sanitised before sharing (`docs/excel-observations.md:256-264`; `tools/sanitize_receipt.py`). "Explicit intent" means the caller names the open workbook as the destination of intention 5; for every other operation the harness's refusal of any open workbook stays the default. The observations this design needs before it is decided: the save form that works after a rebuild; whether Excel's save replaces the file or writes in place; a readable unsaved-changes property; a receipt that records `full_rebuild_invoked` and a save stage.

### 6. Refusal codes and the report shape

| Code | Status | When | Agent surface |
| --- | --- | --- | --- |
| `output_exists` | existing (`catalog/refusal-codes.json:18,143-149`) | intentions 1 to 3: the path exists or is the source | `export_error`. Today the message is `output path already exists` (`agent.py:348`) or `str(error)` (`:355`, `:228`) in Python and `output already exists` (`agent.rs:279`) or `e.to_string()` (`:293`) in Rust; the classified code is computed and dropped. In the race path Python forwards `str(FileExistsError(target))` (`xlsx.py:1104`), a resolved machine path. **Defect, fixed before and independently of G-C:** the message must be the shared refusal text, never the path |
| `revision_conflict` | existing (`:19,150-157`) | `expected_revision` mismatch; stale report; model changed during export | `revision_conflict` |
| `destination_changed` | new | the compatibility test fails before apply; the target is absent or unreadable; post-apply verification finds other bytes and the apply was reversed | `export_error`, message `destination_changed: <observed>` |
| `destination_conflict` | new | `journal_present`; `busy` (the exchange or lock reports another holder); `no_protection` (neither `exchange` nor `lock` offered and no opt-in); `recovery_unavailable` | `export_error`, message `destination_conflict: <reason>` |
| `writeback_unsupported` | new | `no_handle` (bytes import, browser); `no_atomic_rename`; `semantic_only` (intention 4 asked of a fresh-package artifact) | `export_error`, message `writeback_unsupported: <reason>` |
| `envelope_mismatch` | spec 10 Design 5 | the envelope's fingerprint differs from the document's `metadata.source.fingerprint`, once that field exists (G-A) | `export_error`, message `envelope_mismatch: ...` |

The three new codes enter `catalog/refusal-codes.json` and `docs/refusal-codes.md`. Classification is a lowercase-substring search over the shared table, first match wins; Python honours a registered-code prefix before the phrases (`workbook.py:184-192`) and Rust does not (`xlsx.rs:144-179`). So that `WorkbookError.code` and `XlsxError::code()` agree (`python/tests/test_corpus.py:112-135`), each new rule's phrases include the code identifier itself, which both classifiers match in the prefixed message; the three rules are placed before `output_exists` and `revision_conflict`; and the messages above avoid `overwrite`, `already exists` and `model changed`, the phrases those two rules own (`refusal-codes.json:143-157`). Both agents keep `export_error` as the envelope code and carry the prefixed message; that is a message-text change, not a catalog change.

Intention 4 through the agent needs more than a message. The staged, recovery and journal names fail `_FILENAME` (`agent.py:32`) by design, and writeback stages into the source's directory while the agent may write only into `output_dir` (`agent.py:343-346`; `agent.rs:277`). An agent writeback therefore needs a directory-permission model the protocol does not have (the source directory as a declared writable root); it is G-D together with the `plan_export` operation.

Report: `{intention, revision, calc, destination{kind, handle?, identity_before, identity_after}, plan, protection{offered, used, windows[], assumptions[]}, recovery{kind: link | copy, handle, sha256, retained_until | generations}, result{bytes, sha256}, refusals[]}`. Intentions 1 to 3 report `identity_after`, `result` and `plan`. The agent `export` result is `{filename, revision, bytes}` with `additionalProperties: false` (`catalog/agent-operations.json:1877-1882`); adding `sha256` to it, or a `plan_export` operation beside the nine (`CONTEXT.md:49`), changes the catalog and is G-D (open question 4). Library and CLI surfaces carry the full report first.

### 7. Evidence

- A destination whose bytes differ from the fingerprint is refused `destination_changed`; afterwards the destination is byte-identical to before and no stage file, recovery generation or journal remains. A missing destination is refused the same way with `observed: absent`.
- A matching destination is updated; the recovery generation hashes to the fingerprint; every part the plan lists `preserved` is byte-identical to the baseline and the parts that differ are exactly the plan's `rewritten` and `removed` sets. The fixture has a formula on a sheet the edit does not touch (`fixtures/corpus/hb_defined_names.xlsx`: eight formulas on the second sheet, two on the third, edit on the first), so the `cache_refresh` rewrite is measured, and the same test is the acceptance of the writer change in Design 2 if it lands. Reimport of the written file gives the session's values.
- Under hard-link-and-rename an injected in-place writer that finished before the rename is detected and reversed; an injected replace-writer's bytes are lost and the test asserts exactly that, so the unclosed window is a measured fact rather than a sentence; an injected writer that keeps the file open across the rename is reported `open_writer_unclosed`. Under exchange an injected replace-writer is detected and reversed, and a second injected writer between the two swaps leaves a foreign generation that `--recover` lists. Under `recovery: copy` hard-link-and-rename is refused.
- A second writeback on the same target while a journal exists refuses `destination_conflict` (`journal_present`); `--recover` lists an unreadable journal, an orphan stage file and a foreign generation and deletes none of them.
- Intentions 1 to 3 are unchanged: `python/tests/test_toolkit_xlsx.py:63-68`, `test_workbook.py:158-169`, `test_absent_cell_export.py`, `test_agent_python.py:191-201`, `rust/tests/absent_cells.rs`, `rust/tests/corpus.rs:42-64` and `engine.node.test.mjs:205-212` pass unchanged; a Rust test pins the source-overwrite refusal at `xlsx.rs:1966`, which no test does today.
- The regression link runs on the written file: copy `receipts/canonical-operating-scenario/operating-scenario.exported.xlsx`, import it with `import_xlsx`, update it in place with no edits, and `semantic_differences(read_cells(committed), read_cells(written), volatile_rules=rules)` is empty (`test_export_regression.py:74-76,101-115,143-208,238-242`); with `unit_price` 20 to 25 the written caches equal `calculate` on the changed fixture, as the receipt's `after_input_change_preview` lane computes (`canonical_roundtrip.py:99-106`).
- A crash injected after stage, after recovery and after rename each leaves a journal from which `--recover` completes or reverses; the target is never a partial file; the crash after stage restarts from compatibility.
- No report, plan, journal or receipt contains a machine path; a test imports under a directory with a private-looking name and asserts the name is absent from every artifact (`test_canonical_receipt_safety.py` is the pattern). Both agents are forced down the `FileExistsError` race path and the `export_error` message is asserted free of the directory name.

## Open questions for James

1. **G-C, same baseline:** strict fingerprint equality (recommended) or the weaker untouched-parts test, which now needs both the mandatory part-set clause and a `rewritten` set that includes cache-refreshed sheets.
2. **G-C, recovery:** retain until the caller releases (recommended) or a bounded number of generations; location (a sibling `<name>.xlsx.forge-recovery-<hash8>-<n>` is proposed); who may delete.
3. **G-C, protection:** refuse when the destination offers neither `exchange` nor `lock` (recommended), or allow an explicit opt-in to hard-link-and-rename with every window reported. The choice is narrower than it looks: hard-link-and-rename with a reported window is check-then-write with a confession, and under a copy fallback it would be check-then-write without one, so the opt-in is "accept known loss" and nothing softer.
4. **G-D:** whether the agent `export` result gains `sha256`, whether planning and update become agent operations, and whether the agent gets a directory-permission model for the source directory, all of which change the catalog hash. Whether the browser demo defaults `includeLog` on.
5. **Envelope replacement:** a successful writeback replaces the envelope with one derived from the written bytes (spec 10 Design 2). That re-pins any Excel observation taken on the previous bytes as stale; confirm that is acceptable.
6. **Intention 5:** whether the live Excel adapter's destination contract waits for the observations Design 5 lists (recommended) or is decided under G-C now on the docstring alone.
